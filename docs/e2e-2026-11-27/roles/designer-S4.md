Reviewed: S4-01..S4-58 (key screens opened: 03, 07, 18, 23, 25, 35, 37, 40, 45, 51, 55, 57), roles/student.md S4, confusions C68-C92. Source greps in `ui/js/`.
Flow: write netlist in chat (~5.5 min) -> preview -> review/power checks (2-5 min each) -> BOM tweaks -> DFM "Confirm pins" for 8 parts -> Build library (silent for 20 min, then failed) -> Draw in Altium (refused, split to 3 sheets, drawn in 55 s) -> ERC and NC questions. About 55 screenshots; the stage was dominated by waiting and by library-build problems, not by drawing.

## Findings

- [BLOCKER-class friction] The 20-minute silent build and its error: S4-21..S4-23, S4-38..S4-40 (C77-C79, C84-C86). Build library for one new 10 nF cap reset the whole BOM to "31 to verify (library)" (S4-21), ran 15-20 min with only "Building in Altium. It can take a few minutes" (ui/js/views/bom.js:151), vanished from the page after a reload while the button looked active again, and a second click produced "Altium is still working on another step; wait for it to finish and try again" (S4-23). The first run ended with no message at all (C85). The eventual error (S4-40) is a 6-line red block with a Windows path telling the student to "restart Altium" and use "Projects panel, right-click, Add Existing to Project", with no button. Four UI failures: (1) no timeout or elapsed time and no "this is taking too long"; (2) the running state is client-side only (`libBusy`, bom.js) so a reload loses it; the server must report it; (3) silent end: a build that ends without a result must say "Build ended without a result"; (4) an error the tool cannot fix must say so plainly and give a button ("Restart Altium and retry") instead of Altium menu steps for a student who must not touch Altium. Also adding one part should build one part (C77: "31 to verify" for everything).
- [FRICTION] The product tells the student to press a button that cannot work: S4-02/S4-03 (C68). The Schematic page is a blank box with the filename; chips and every agent answer say "press Draw in Altium"; pressing it gives a red "There is no netlist sheet to draw: ask the agent in the chat to write the schematic first." Fix: on an empty schematic show one primary "Write the schematic" button (it sends the request), disable Draw with the reason in its tooltip, and make the "Next:" line say the same. Source ui/js/views/previews.js (schematic view), chat chips ui/js/chat.js:608-617.
- [FRICTION] Draw refused after the agent wrote a netlist it could not draw: S4-45, S4-46 (C88). The error is clear and specific ("needs about 3 sheets ... nets that would cross: BOOT0, BOOT1, ...") and has "Show details", which is good; but the student only learns the limit after pressing Draw, the page header said "1 sheet", and the preview showed one big sheet. Fix: the preview/header shows "Fits 1 sheet: no" before the draw, and the agent's netlist step checks it. The banner is placed over the preview (S4-45) and hides it; put it above the preview.
- [FRICTION] Long waits with a bare counter: netlist ~5.5 min (S4-05, S4-06 "Working... 75 s / 200 s"), "Review this sheet" ~5 min, other answers 2-5 min (C69, C71). The same finding as every stage; Antigravity shows no step list here (compare Claude Code "Steps (n)"). Fix: named steps and an estimate for both engines (progress block in ui/js/chat.js).
- [FRICTION] Duplicate and conflicting messages after the netlist: S4-07 (C69). An amber "netlist.write applied with warnings" block (internal action name again, chat.js:522-535) followed by "After the results - Correction: ..." that repeats it with a different part list (J1, U1-U5, D1, D2, J3 vs "J1-J3, Y1-Y2, D1-D4"). Then after the rewrite (S4-48) the same "guess" warning returns for parts the student had already confirmed (C89). Fix: one message, one list, and confirmations survive a netlist rewrite when the pins are unchanged (state is per part, not per write).
- [FRICTION] The schematic preview is not readable for review: S4-07, S4-08, S4-57 (C70). Six small blocks, nets as text stubs, pin names invisible at Fit, 49-pin U1 symbol unreadable. The student had to read the page text to check anything. UI-SPEC tab 3 asks for an interactive preview with one-click "Ask about this" on a part or net. Fix: zoom to a part on click, hover shows net name, a net list/part list side panel; add "Ask about this" on click. Source ui/js/views/previews.js (schematic), ui/js/diagram.js not relevant.
- [FRICTION] "Confirm pins" dialog is the most laborious screen of the stage: S4-25..S4-29 (C80). The first page chip opens p.190, a blank last page (S4-25); the next chip is the UFBGA100 pinout, not the student's UFQFPN48 package; the pin list has 49 rows with a "wrong" checkbox each, scrolled separately from the PDF. Fix: open at the page that holds the package's pin table, group the pins (power / debug / signals) and show only the pins that matter first, one "Pins match" button (exists, good) plus "Show all pins". Source: the dialog in ui/js/views/pages.js (DFM unverified parts) and ui/js/viewer.js.
- [FRICTION] Inconsistent paths in DFM > Unverified parts: S4-35, S4-36 (C81, C82). U1-U5 have a Confirm pins dialog; D1/D2/J3 have only text and "Confirm all (3)", which would also accept J3 whose datasheet is unreadable; clicking the D1/D2 rows and "Check datasheets" does nothing visible. Fix: every row opens its datasheet/pins dialog; "Confirm all" excludes parts that cannot be checked and says why.
- [COSMETIC] The honest split is good but the labels clash: S4-37 DFM shows "Checked by you" for U1/U2/U4/U5 while the BOM Status column shows "Accepted risk" for the same parts (S4-40, C84). Two names for one state. Fix: BOM status says "Pins checked" vs "Accepted risk" exactly as DFM does. Source bom.js status cell (:71-81).
- [FRICTION] "Pins conflict" chip with no explanation: S4-17, S4-18 (C75, C76). Clicking it opens an Alternatives panel (including Keystone 5128/1280 which are not flash parts) instead of saying what conflicts (pin 7 name IO3 vs /HOLD); the BOM message "1 part needs your own look U4" and "Confirm all (6)" excluding it adds to the confusion. Fix: the chip opens the conflict (pin, symbol name, datasheet name) with one "Accept" button; Alternatives only on request.
- [FRICTION] The drawn result is shown as warnings only: S4-51, S4-56 (C90). "54 parts and 38 nets drawn on 3 sheets, saved and checked against the netlist" is the good news but it is the first line of an amber banner; the 3 warnings (two A3 sheets, a D1 symbol-line warning) are then repeated as a second amber block in the chat. The student could not tell whether D1 (the ESD part on VBUS) was a short. Fix: green success banner "Drawn: 3 sheets, 54 parts, 38 nets" + a separate collapsible "3 notes"; each note says whether it matters ("A3 sheets: fine", "D1 symbol line: not a short, see ...") instead of leaving it to a chat question. A good detail: the sheet tabs "02 Clocks, reset, boot, SWD and sensors / 03 Flash... / Main..." (S4-51, S4-57) are clear.
- [FRICTION] The app cannot fix what it built, and the fix is Altium work: S4-53 (C91). The D1 warning will come back on every draw; the answer says edit the SchLib and run Update From Libraries, plus "run Project > Validate PCB Project in Altium". The same missing pattern as stage 3: no "You fix in Altium" state with steps and a Done box, and the Schematic page does not show open items. Fix: the item list pattern proposed in designer-S3 (per-item state: tool fixes / you fix / ignore), applied here.
- [FRICTION] ERC/NC results live only in chat: S4-53..S4-55 (C91, C92). The student asked for ERC and unused pins in chat; the answer is a table of 17 pins with "marked NC with No ERC markers" (contradictory phrasing), and there is no page element for "open pins / NC: 0 open" or "ERC: 0 errors". UI-SPEC says checks are visible on the page. Fix: a small status line on the Schematic header: "ERC 0 errors, 0 warnings - 17 pins marked no-connect - 0 open", clickable to the table.
- [FRICTION] The agent adds unrelated news to a simple approval: S4-15, S4-16 (C72, C74). A BOM card shows "R5" for what the text calls R14 (a quantity bump, so the card looked like the wrong part); after approval the agent adds "the board is 64% covered, try 60x45" (a design suggestion at stage 4), and the BOM badge shows "1 open". Fix: card title names the new ref ("R14 new (line R5 qty 3 to 4)") and board-area advice goes to the Layout page.
- [COSMETIC] Build/Draw hand-offs mix buttons and text: "Next: press Draw in Altium ... or tell me to draw it" (S4-13, S4-20) - after the draw the chip changes to "Help me with the next step: Place parts" (S4-51): good. But in between (S4-13, S4-20) the next-step line was still "Draw" while "Build library" was needed first (S4-20 "Next: review C23 and rebuild the library"). The chip order should follow the true order: library -> draw.
- [COSMETIC] Left menu Rules badge "6" with no board is still there (S4-03, S4-45).
- Good: schematic tabs per sheet; error with "Show details"; "Checked by you" vs "Accepted risks" with Revoke buttons and an Undo toast "3 parts confirmed - Undo" (S4-37); after the draw, an honest 55 s result with counts; the "Place parts" chip after drawing; citations with quotes under the ERC/NC table (S4-55).

## Score and fixes
Score S4 (UI/UX only): 5/10. The drawing itself worked and has good touches (sheet tabs, "Show details", Checked vs Accepted split), but the stage was dominated by a silent 20-minute build with a hard-to-act-on error, buttons the product told the student to press before they could work, a preview too small to review, and a very laborious Confirm-pins path.

Top 3 fixes:
1. Make long Altium steps observable and recoverable: server-reported running state (survives reload), elapsed time and a timeout message, a result for every run (even "ended without a result"), and errors the student can act on with a button instead of Altium menu steps; build only the new part (ui/js/views/bom.js:151 and the `libBusy` logic, server state for build, error banner component).
2. Keep the "next step" truthful: derive the Next line and chips from the page state (empty schematic -> "Write the schematic"; library dirty -> "Build library"; sheet does not fit -> say before Draw), and show success as success with notes collapsed (ui/js/chat.js:608-617, ui/js/views/previews.js schematic header and banner).
3. Make verification fast and consistent: Confirm pins dialog opens on the right package page with grouped pins, every unverified row opens it, "Confirm all" excludes unreadable parts, and BOM/DFM use the same labels (ui/js/views/pages.js DFM unverified parts, ui/js/viewer.js, ui/js/views/bom.js:71-81).
